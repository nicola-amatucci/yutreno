# YuTreno repository rules

## Architecture
- `src/core/` is the simulation core: line, train, signalling (ETCS L2 and automatic block + SCMT), supervision, dynamics, observation and command API. It does not depend on the DOM nor on Node: it must run the same in the browser, in Node and behind a server.
- `src/web/` is the interface (3D cab view in `view3d.ts` with Three.js, fallback 2D view, DMI, editors, in-browser controllers). It reads the state of the core and sends it commands; it contains no physics or signalling logic. The 3D world is a deterministic function of the compiled line.
- `docs/ROADMAP.md` (Italian copy `docs/it/ROADMAP.md`) says where the project stands, what the owner decided and what comes next: read it before starting, and update it when a step of the plan is done or a decision is taken.
- `docs/ARCHITECTURE.md` describes data flow, fixed step, 3D view and the points to touch for frequent changes: it must be updated when they change. `docs/design/` has one design document per component, to update with the component.
- `src/server/` contains the Node tools: headless execution and the bridge from the page to TCP or a process (`bridge.ts`) for external programs.
- `src/docs/` contains the page describing the dynamics model; it uses the core for its charts, so it must be checked again when the model changes.
- `examples/` contains the example controllers (JavaScript and Python) and the external dynamics models (JavaScript, Python, Octave, MATLAB). `docs/` contains guides, API, model, standards, design documents, external dynamics, ETCS onboard, guide to connect an EVC, trackside and architecture; `docs/it/` the Italian copies. `examples/openetcs/` compiles the openETCS code outside the repository (`openetcs-build/`, ignored by git).
- Names are in English; where a standard exists, the names of the standard (Subset-026 variables, EULYNX telegrams). The Italian names of version 0.x stay accepted on input through `src/core/legacy.ts` (`toEnglish`) and are produced for legacy programs with `toLegacy` (observation versions 1 and 2, protocol version 1). A field born in English needs nothing in the glossary; renaming a field that existed in 0.x requires its entry in `KEYS_IT_EN` or in the value maps.
- With `model: 'external'` the dynamics comes from an external program in co-simulation (`docs/EXTERNAL_DYNAMICS.md`). The protocol is a public interface: new response fields must be optional, and `examples/dynamics_point.js` must keep reproducing the internal `point` model (`verify-external-dynamics`).
- With ETCS and `onboard: 'reference' | 'external'` the supervision is done by an onboard computer that speaks with Subset-026 balises and messages (`simple-rbc.ts`, `evc.ts`, `docs/ONBOARD_ETCS.md`). `evc.ts` must not import anything from the engine except the protocol types and `legacy.ts`; the protocol is a public interface like that of the external dynamics.
- With ETCS, a message-based onboard and `trackside: 'interlocking' | 'external'` the authority comes from the trackside component in `src/trackside/`: interlocking with EULYNX SCI-P and SCI-TDS telegrams, RBC that builds the authority from the routes, RFI-style control table with the translator (`docs/TRACKSIDE.md`). The engine simulates only the field (`src/core/field.ts`) and imports `../trackside`; `src/trackside/` imports nothing from the engine except types and `legacy.ts`. The engine–trackside protocol is a public interface: new fields must be optional, and `examples/trackside/trackside_stdio.ts` must give the same run as the in-process trackside (`verify-trackside`). With `trackside: 'simple'` (default) the results must not change: the numbers of the reference campaign stay those of before.
- The controller observation has three versions: version 3 (default) has English names and contains `etcs_ato` with the Subset-130 ATO data (`EtcsAtoData`), computed by `atoData()` in `signalling.ts` or provided by the onboard in the optional field `dmi.ato`; version 2 is version 3 with the Italian names; version 1 is version 2 without `etcs_ato` and must stay identical. `examples/ato_s130.js` is the second reference ATO: stops, vigilance and regulator stay equal to those of `examples/ato.js`, so that the comparison between the two measures only the use of those data.
- The simulation advances with a fixed step (`FIXED_DT`, 5 ms) and is deterministic: with the same line, train, scenario and commands it produces the same data. Every change must preserve it.

## Commit rules (atomic blocks)
- **Small, logical, self-contained commits.** Do not put different features, subsystems or layers in the same commit. Split them into atomic commits (for example: line model → signalling → dynamics → interface → checks), so that `git log` tells every addition by itself.
- **Add the files of each block explicitly.** Use `git add "<file1>" "<file2>" ...` only with the files of that block. Do not use `git add -A` or `git add .` when the working tree has unrelated changes.
- **Conventional Commits.** Every message has the form `<type>(<scope>): <summary>`, for example `feat(core): ...`, `feat(etcs): ...`, `feat(web): ...`, `fix(physics): ...`, `test(verify): ...`, `docs(api): ...`.
- **Check before committing.** `npm run typecheck` and `npm run verify` must pass before closing a commit that touches `src/` or `scripts/`.

## Commands
- `npm run build`: creates `dist/index.html`, `dist/yutreno.html` (single file, opens with a double click) and the model page `dist/model.html`.
- `npm run dev`: development server with automatic rebuild.
- `npm run typecheck`: `tsc --noEmit` on the core and on the web interface.
- `npm run verify`: all the scripts `scripts/verify-*.ts`, as many at a time as there are processors (`-- --jobs 1` one after the other, `-- <name> ...` only some).
- `npm run golden`: the golden master (`golden/fingerprints.json`): runs every scenario and scenario configuration in six variants of signalling, onboard, trackside and regulator, and the two campaigns, and fails if any part of any run changed (samples, events, timetable, passengers, summaries, dispatcher, control room). A change meant to leave the behaviour alone (refactoring, phase 8) must keep it unchanged; a change of behaviour on purpose updates it with `-- --update` in the same commit. `-- --only <text>` runs a subset, `-- --quick` only the scenarios as written (about a minute); `npm run verify -- --quick` runs only the short checks. The quick forms are for everyday work: the whole set stays required before a commit.
- `npm run build` then `CHROME=/usr/bin/google-chrome node scripts/page-golden.mjs` (Playwright): the golden master of the page (`golden/page.json`): text and fields of every tab and the description of the 3D scene for 24 states, with the clock of the page replaced by a manual one. A change of `src/web/` meant to leave the page alone must keep it unchanged; a change on purpose updates it with `--update` in the same commit.
- `npm run headless -- --help`: runs without graphics, with a JavaScript or external controller via WebSocket; `--scenario <file|folder>` runs scenarios with verdict; `--dynamics <tcp://|ws://|exec:command|file.js>` uses an external dynamics model; `--onboard <internal|reference|tcp://|ws://|exec:command|file.js>` chooses the ETCS onboard; `--trackside <simple|interlocking|exec:command|tcp://|ws://>` chooses the trackside (only with a message-based onboard); `--protocol 1` speaks the Italian protocol of 0.x with external programs.
- `npm run bridge -- --tcp localhost:5555` (or `--exec "command"`): takes the page (ws://localhost:8766) to a dynamics model on TCP, for example MATLAB, or to a process on stdin/stdout, for example Octave.
- `npm run campaign`: onboard × ATO × scenario measurement campaign with and without faults (`campaigns/reference.json`, `docs/CAMPAIGN.md`); writes in `results/` (ignored by git) deterministic CSVs with run fingerprints and determinism checks. If a change modifies the results on purpose, the numbers in `docs/CAMPAIGN.md` are updated in the same commit.
- `npx tsx scripts/curve-validation.ts`: points of the reference onboard curves for the cases of `validation/cases.json`, to compare with the ERA tool (`docs/CURVE_VALIDATION.md`).
- `docs/traceability/matrix.csv`: requirement matrix of Subset-026, Subset-130, EULYNX and the control table. If a change modifies what the onboard, the trackside or the protocol implement, the corresponding row is updated in the same commit. Tests that check a requirement carry a tag `// @test <id>: <title> [<requirement ids>]`; after adding or changing tags run `npx tsx scripts/traceability.ts`, which regenerates `docs/traceability/tests.csv` and the `tests` column. `verify-traceability` fails if an implemented or simplified row has no test.
- `npx tsx scripts/measure-realtime.ts`: real-time measures (`docs/REAL_TIME.md`); the results depend on the machine and go in `results/`.
- `docker build -f docker/Dockerfile -t yutreno-demo .` and `docker run --rm -p 8000:8000 -p 8766:8766 -p 8767:8767 yutreno-demo`: complete test environment with demo (`docker/`). If an external example is added, consider adding it to `docker/demo.sh`.

## Scenarios
- Scenarios are in `scenarios/` (those of the interlocking trackside in `scenarios/trackside/`, those with service trains in `scenarios/services/`) and are also included in the page (`src/web/scenarios.ts`). A new scenario must be added in both places and its outcome with `examples/ato.js` recorded in `scripts/verify-scenarios.ts` (`docs/SCENARIO_GUIDE.md`); service scenarios are checked in `scripts/verify-services.ts` instead.

## Documentation
- The main documents are in English in `docs/`; the Italian copies in `docs/it/` must be kept aligned when a document changes in substance.
