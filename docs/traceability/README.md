# Traceability

This folder holds two files:

- `matrix.csv` compares YuTreno with Subset-026 v4.0.0 (ERTMS/ETCS System Requirements Specification) with Subset-130 v1.0.0 (interface between ETCS onboard and ATO), with Subset-039 v4.0.0 (RBC/RBC handover) and, for the moving block, with four requirements of the X2Rail-5 Moving Block Specification (`X2R5-MB-*`), which is not a TSI document. At the bottom there are also the rows of the interlocking trackside: the EULYNX telegrams used between interlocking and elements, the interlocking–RBC and interlocking–control centre interfaces, which EULYNX does not publish and YuTreno invents, and the reconstructed control table (see [TRACKSIDE.md](../TRACKSIDE.md)). The last rows record the sources of the operational models: network topology, capacity (UIC 406), rerouting, rostering and connections, infrastructure import, scenario configuration and the passenger model. It tells what of the code holds with respect to the standard, what is simplified and what is missing, before writing any statement that uses it.
- `tests.csv` lists, for every requirement, the tests that check it: one row per (requirement, test), with the script and the title of the test. It is generated by `scripts/traceability.ts` from the `@test` tags of the verify scripts and must not be edited by hand.

The reference text are the official ERA PDFs of v4.0.0, the one of TSI 2023. In Italy Baseline 3 (v3.6.0) is in service. In the parts that matter here the most visible differences concern the braking times, which in v4.0.0 separate the reaction (`T_be_react`) from the build-up and introduce the reduction per target (A.3.12). For a comparison with v3.6.0 those rows must be reviewed. How YuTreno relates to each standard is discussed in [STANDARDS.md](../STANDARDS.md).

## How the matrix is made

The matrix has two levels, so as not to become unmanageable.

**Per section**: chapters 3, 4, 5, 7 and 8, one row for every section down to the third level of numbering, taken from the titles of the specification. It is enough to see at a glance what is there and what is missing.

**Clause by clause**: only §3.13, in the parts that the reference onboard declares to implement (braking curves, supervision limits, commands), and the variables of packets 6 and 11 of Subset-130. That is where the validity of statements about the onboard is decided.

Every row has these columns:

| Column | Content |
| :-- | :-- |
| `id` | identifier of the row, used by the test tags (for example `S026-3.13.8.3.2-c` for a clause, `S130-Packet-6-N_LOC_EBI` for a variable) |
| `specification`, `level`, `reference`, `title` | where the requirement comes from |
| `component` | trackside, reference onboard, protocol or engine |
| `status` | see below |
| `code_location` | where it is in the code |
| `tests` | the tests that check it (generated; `via sub-clauses` for a section covered through its clauses) |
| `deviation` | the deviation from the text |
| `relevant_for_results` | whether the row affects the numbers produced by the reference onboard and the campaign |
| `validation_judgement` | empty column for the validation of the row against the text of the specification by a domain expert |

There are five statuses:
- **implemented**: it does what the clause asks, within the limits of the data it receives;
- **simplified**: it is there, but with declared deviations that should not change the substance;
- **divergent**: it is there, but does something different from the text, in a way that changes the numbers;
- **missing**: it is not there;
- **out of scope**: it does not concern a level 2 bench in full supervision (Euroloop, infill, national systems, juridical recording, DMI).

## Tests and traceability

Every test block that checks a requirement carries a tag line in its script:

```ts
// @test S16: EBI position before the EBD by the reaction time, N_LOC_EBI [S026-3.13.9.3.2.12-c, S026-3.13.6.2.2.3-c, S130-Packet-6-N_LOC_EBI]
```

`npx tsx scripts/traceability.ts` collects the tags of all `scripts/verify-*.ts`, writes `tests.csv` and fills the `tests` column of the matrix. It also checks that:
- every requirement named in a tag exists in the matrix;
- every **implemented** or **simplified** row has at least one test, on the row itself or, for a section, on one of its clauses.

`npm run verify` includes `verify-traceability`, which fails if one of these conditions is not met or if the two files are not up to date. So a change that adds a function without a test, or a test that refers to a wrong requirement, does not pass the checks.

Most requirement tests are in `scripts/verify-subset026.ts`: 25 blocks that drive the reference onboard cycle by cycle with hand-built telegrams and messages and compare its behaviour with the clause, in closed form where the clause gives a formula (EBD and SBD with the gradient and rotating mass correction, EBI with the build-up time, SBI1/SBI2, ceiling margins). The others are in the system-level scripts (`verify-onboard`, `verify-trackside`, `verify-ato-s130`, `verify-scenarios`, `verify-curve-validation`), tagged with the rows they cover. Today 132 tagged tests in 18 scripts cover all 205 implemented or simplified rows.

A test shows that YuTreno does what YuTreno declares, with the simplifications of the matrix. It does not show conformity to the specification: that would require the Subset-076 test sequences on a product, which is out of the scope of a research simulator.

## What it says

Out of 231 sections of chapters 3, 4, 5, 7 and 8:
- 3 are implemented;
- 77 simplified;
- 9 divergent;
- 122 missing;
- 20 out of scope.

It is the honest portrait of an onboard that covers full supervision in level 2 and almost nothing else: it has no start of mission, no modes beyond SB, FS, TR and PT, no version management, no bit encoding of the messages, no special functions.

In the detail of §3.13, out of 57 clauses:
- 20 are implemented;
- 19 simplified;
- 3 divergent;
- 15 missing.

The divergent ones and the missing ones that change the curves are those to look at first, because they affect the results.

1. **Gradient and train length (3.13.4.2.1, divergent).** The specification takes the most unfavourable gradient under the whole fictitious train. The onboard uses the gradient at the location of the head. On a descent that starts after a level stretch the onboard is **less cautious**.
2. **Emergency times (3.13.9.3.2.3 and .6, divergent).** The specification splits the time between traction still present and braking building up, and the two times overlap. The onboard adds them. The dead time is longer, so the onboard is **more cautious**.
3. **Estimated acceleration and speed error (3.13.9.3.2.1, .8, .9, missing).** When the train accelerates towards a target the onboard is **less cautious**. The odometry of the engine is exact, so V_ura would have no value to use anyway.

Two divergences have been corrected. The SBI2, W, P and I limits of a speed reduction (3.13.9.3.3.2, 3.13.9.3.4.1, 3.13.9.3.5.1, 3.13.9.3.6.1) used to come from curves towards V_target + dV_sbi, V_target + dV_warning and V_target, which made the permitted speed lower and earlier than the text; they now come from the EBD of the target, towards V_target + dV_ebi, shifted by the times, as for the end of authority. The indication time (3.13.9.3.6.2) now includes T_driver. Test S25 of `verify-subset026` checks both in closed form.

The correction concerns the measurement campaign directly, because the simple ATO follows the permitted speed of the onboard. Its numbers are in [CAMPAIGN.md](../CAMPAIGN.md): with the reference onboard the simple ATO now consumes slightly more (a later and higher permitted curve before every speed reduction), while the Subset-130 ATO, which plans on the EBI, is unchanged. The conclusion of the campaign does not change. The results still hold **for this onboard**, which is not yet validated against the ERA tool.

## How to check it

The matrix was written by reading the code and the text, and it is an interpretation: it must be checked. The recommended order starts from the rows with `relevant_for_results = yes` and status divergent, then simplified. For each one:
1. read the clause in the PDF of the specification;
2. read the point of the code given in `code_location` and the tests in `tests`;
3. write in `validation_judgement` whether the status is right, or what to change.

The CSV opens with any spreadsheet. If a row changes status, it must be changed here and in the code in the same commit, and `npx tsx scripts/traceability.ts` run again.
