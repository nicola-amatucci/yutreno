Model and simplifications

The motion follows the traction equation: the equivalent mass, that is the mass increased for the rotating parts, accelerates under the difference between the tractive effort and the sum of brake, Davis resistance R = A + B·v + C·v² and weight along the gradient. The gradient is the average one under the whole length of the train, so a long freight train feels a hump gradually. The physics advances with a fixed step of 5 ms: with the same commands two runs produce the same data.

The effort is limited first by the maximum force, then by the power (it decreases as 1/v) and finally by adhesion: μ times the weight on the motored axles in traction, μ times the total weight in braking. When the demand exceeds adhesion, SLIP or WSP light up and the force is cut. Braking uses the electric brake first, which regenerates energy, then the pneumatic one.

In ETCS level 2 mode there are no lineside signals: the RBC grants a movement authority up to the start of the first occupied section, with a danger point 50 m beyond. The internal onboard builds the indication, permitted, warning, service brake intervention and emergency brake intervention curves, correcting the deceleration for the steepest descent and for adhesion. With the reference onboard the curves follow the models of Subset-026 chapter 3.13. With the automatic block the protection is a simplified SCMT.

In the cab view the altitude profile is exaggerated twice to make climbs and descents perceptible.

Parameters

Davis resistance: A in kN, B in N/(m/s), C in N/(m/s)². The decelerations are the nominal ones on dry rail; the simulator reduces them if adhesion is not enough.

Consist and couplers

With the external model the train dynamics is computed by an external program, for example MATLAB/Simulink, which the page queries at every coupling interval. The consist stays available to the model, which receives it at the start of the run. For MATLAB listening on TCP the bridge npm run bridge is needed; the protocol is in docs/EXTERNAL_DYNAMICS.md.

With the multi-mass model, mass, length and motored share of the train are derived from the consist. The pneumatic brake reaches the vehicles with the propagation delay along the brake pipe; the electro-pneumatic one reaches all of them at once.

Make a scenario: line, trains, passengers

The driven train keeps the timetable of the line; the service trains repeat it every given number of minutes, or are those of the real timetable when the line has one. With passengers, every station sends that many people an hour, spread evenly over the stations it can reach; they board, alight, set the dwell times and add to the mass of the trains (docs/PASSENGERS.md). The same scenario can be written as a short JSON and run without the page (docs/SCENARIO_CONFIG.md).

Description

Events in the current run

Events that are not announced, such as leaves or a degrading brake, are shown neither to the driver nor in the controllers' observations: they stay only in the log, for the analysis.

Verdict

The verdict uses the criteria of the scenario; those not given take the default values: run completed, no missed stop, stop error within 5 m, no protection intervention, no overrun, no missed vigilance.

JSON definition

Edit the JSON to create your own scenario. Event types: radio_loss, speed_restriction, low_adhesion, brake_degraded, traction_reduced, leader_stopped, rbc_emergency_stop, message, point_failure, tvps_failure, operator_command. The complete format is in docs/SCENARIOS.md, the step-by-step guide in docs/SCENARIO_GUIDE.md. Scenarios written with the Italian names of version 0.x are still accepted.

Checks of the planned timetable

    The line between stations is single track and every station has a track for each direction: two trains can cross or overtake only in a station.

    Import and export

    Import reads a GTFS archive, a NeTEx document (Italian profile or others) or a railML 2 or 3 timetable and replaces the services being edited: stops are matched to the stations of the line by name, the trip with the timetable of the line is the controlled train and is left out. Downloads contain the timetable in use, with the controlled train as R 2001; railML also carries the minimum dwells. GTFS and NeTEx use the same identifiers as the real-time feeds of npm run feeds.

        Simulator and controller run in lockstep: at every period the simulator sends an observation and stops until the command arrives. The results therefore do not depend on the speed of the computer. The external controller works by opening the page locally (dist/yutreno.html or npm run dev), because inside a page published as an artifact network connections are blocked. For batch runs without graphics use npm run headless.

        API reference
        
      
        At every period the simulator sends a JSON observation object. The controller responds with a JSON command: omitted fields leave the previous command unchanged. Quantities are in SI units: metres, seconds, metres per second. Positions are chainages from the origin of the line and refer to the head of the train. This is API version 3; the full reference is in docs/API.md.
